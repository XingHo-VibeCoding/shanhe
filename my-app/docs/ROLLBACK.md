# 诗迹山河 · 回滚手册

> 什么时候翻开它：线上出问题、拿不准要不要退、或者要演练回退时。
> 核心原则：**先让线上恢复可用，再查原因**；能退就退，别带着故障硬修。

---

## 一、先搞懂：本站的"回滚"是什么

线上跑的不是 GitHub 上的代码，而是**"最后一次部署时，你本地的那份代码"**（部署动作叫「发布为应用 / sites deploy」）。

所以回滚 = **两步**：

1. 把本地代码切回上一个版本（`git checkout <目标提交>`）
2. **重新部署一次**

只做第 1 步没用，线上不会变。这一点是本项目最容易踩的坑。

---

## 二、什么情况必须回滚（判断表）

| 信号 | 典型例子 | 要不要回滚 | 理由 |
|---|---|---|---|
| 线上整站打不开 | 首页 502 / 全站白屏 | ✅ 立刻回滚 | 用户立刻受影响，先恢复 |
| 核心功能坏了 | 搜索全部报错、详情页渲染不出 | ✅ 立刻回滚 | 主链路断了 |
| 错误已扩散给用户 | 脏数据已展示、错误结果已供出 | ✅ 先回滚再修数据 | 先止损，后返工 |
| 只是样式小瑕疵 | 某处间距不对、颜色偏了点 | ❌ 不用回滚 | 直接小修即可，回滚反而丢新功能 |
| 内容层面的小错 | 某一首诗的译文有误 | ❌ 不用回滚 | 这是数据问题，改数据、不动代码 |
| 只有本地能看到的问题 | 本地没重启、开了多个后端进程 | ❌ 不用回滚 | 先排查本地，别误伤线上 |
| 拿不准影响面 | | ⚠️ 先停下确认 | 回滚有成本，先搞清影响范围 |

**口诀：用户"用不了"就回滚，只是"不好看/差一点"就先小修。**

## 三、路径 A：整站代码回退（主力路径，Day 26 已实测）

适用：绝大多数情况（前端 + 后端都在同一个仓库）。

### 标准步骤

1. **确认退回哪个版本**（见第五节「版本速查」）
2. **确认工作区干净**：`git status --short`，已跟踪文件应无改动
3. **切到目标版本**：`git checkout <目标提交>`（会进入 detached HEAD，属正常）
4. **重新部署**：用 WorkBuddy 的「发布为应用」重新部署 `my-app`
5. **验证**（见第四节「验证靶子」）
6. **恢复时**：`git checkout master` → 重新部署 → 再验证一次

### 实测耗时（Day 26 演练，2026-10-14）

| 动作 | 耗时 |
|---|---|
| 回退到旧版 `e86b375` | **73 秒** |
| 恢复到 `3f3921b`（v1.0） | **55 秒** |

结论：从"决定要退"到"线上变旧版"约 1 分多钟，恢复也在 1 分钟内。真出事时来得及。

## 四、回滚后怎么验证（别只看"打得开"）

用**一眼可辨的靶子**，否则分不清到底退成功没有：

- **搜「李」**
  - 新版（v1.0）：李白《将进酒》排第一
  - 旧版（`e86b375`）：6 首显示为「佚名」
- **主页与五个页面**：`home / index / detail / footprints / mock` 都应 HTTP 200
- **四个接口**：`/api/health`、`/api/hot`、`/api/favorites`、`/api/checkins` 都应返回 `ok:true`
- **跑一遍发布前检查**（最省事，一次全查）：

```
C:/Users/23850/.workbuddy/binaries/python/envs/default/Scripts/python.exe my-app/tools/pre-release-check/check.py
```

5/5 全过才算恢复成功。报告自动存到 `.workbuddy/reports/pre-release/`。

## 六、路径 B：云函数回退（备查，Day 26 未实操）

本站四个云函数（`api-checkins` / `api-hot` / `api-favorites` / `api-health`）跑在腾讯云 CloudBase。

- 控制台方式：「云函数」→ 选中函数 → 版本管理 → 回退到上一个版本
- CLI 方式：`tcb fn deploy <函数名> -e <envId>`
- 注意：云函数与前端相互独立，前端回滚**通常不必**同时回退云函数。只在前端回滚后接口仍报错时，才怀疑云函数。

## 七、路径 C：数据恢复（备查，Day 26 未实操）

- **本地诗歌库** `poems.db`（32.6 万首）：定期把 `poems.db` 复制一份做备份
- **云数据库**（checkins / favorites）：CloudBase 控制台「数据库」→ 备份 / 回档
- **红线**：恢复数据前**必须先备份当前状态**，禁止直接覆盖。数据不像代码，退错了可能真的找不回。

---

## 八、红线（务必遵守）

- 禁止 `git reset --hard`、禁止强制推送
- 回滚前先确认工作区干净，避免把未提交的改动一起带上去
- 回滚只是"先恢复可用"，**不是**"把问题盖住"；恢复后一定要把根因查清并补上修复
- 每次回滚都留记录：时间、从哪个版本退到哪个版本、耗时、验证结果
